## 一、产品定位

### 1.1 这个 AI 工作台解决什么问题

**核心问题**: 游戏公司在日常运营中面临"决策碎片化、数据孤岛、协同低效"三大痛点。

| 痛点 | 具体表现 | 造成的损失 |
|------|----------|------------|
| 决策碎片化 | 买量、LiveOps、商业化、产品迭代各自为政, 缺乏统一决策中枢 | 预算浪费, 互相冲突 (如买量拉新与 LiveOps 召回争夺预算) |
| 数据孤岛 | Meta Ads 数据、玩家行为数据、工单数据、收入数据分散在不同系统 | 决策延迟, 无法形成闭环反馈 |
| 协同低效 | 产品→策划→开发→测试→上线→买量→运营链路靠人工传话 | 交付周期长, 信息损耗大 |
| 经验不沉淀 | 每次决策都是"从零开始", 成功/失败经验未结构化存储 | 重复犯错, 无法复用最佳实践 |

**解决方式**: 构建一个"虚拟游戏公司", 用 AI Agent 模拟真实游戏公司的 14 个职能部门, 在统一工作台内完成从市场洞察到 LiveOps 运营的全链路协同, 所有决策数据自动流转并沉淀为组织记忆。

### 1.2 用户是谁

| 用户角色 | 使用比例 | 核心诉求 |
|----------|----------|----------|
| 游戏公司 CEO/创始人 | 20% | 全局掌控公司状态, 审批重大决策, 把握战略方向 |
| 发行人/制作人 | 30% | 监控游戏组合健康度, 协调跨部门资源, 推动项目交付 |
| 买量/UA 负责人 | 20% | 优化广告投放, 控制 CAC, 提升 ROAS |
| LiveOps/运营负责人 | 15% | 流失预警, 回流活动, 生命周期管理 |
| 数据分析师 | 15% | 自动化报表, 异常检测, 深度归因 |

**核心用户画像**: 中小型游戏公司 (10-100 人) 的决策者, 希望用 AI 替代部分人工岗位, 降低运营成本, 提升决策效率。

### 1.3 使用场景

**场景 1: 每日晨会 (CEO 视角)**
> CEO 打开 Dashboard, 看到 AI CEO 已完成每日例会: GrowthLoop 昨夜自动暂停了 3 个 ROAS 低于阈值的 campaign, 节省 $2,400; LiveOps Agent 识别出 87 个高价值流失玩家并设计了回流活动; 数据分析师生成了昨日 BI 报表并标记了 2 个异常指标。CEO 只需审批 3 条待决策事项。

**场景 2: 新游立项 (制作人视角)**
> 市场研究部发现 "Merge + Simulation" 品类在东南亚市场搜索量上升 340%。产品部自动生成 PRD 草案, 游戏策划部产出 GDD 和关卡设计, 商业化部评估 LTV/CAC 可行性。制作人在工作台查看全链路产出, 决定 Go/No-Go。

**场景 3: 买量优化 (UA 负责人视角)**
> UA Agent 从 Meta Ads 拉取实时数据, 发现某 creative 疲劳度上升。Creative Agent 生成 3 个变体方案, 审批后自动上传。72 小时后数据分析师回测效果, ROAS 提升 18%, 经验自动写入 AI 记忆中心。

**场景 4: 流失召回 (LiveOps 视角)**
> 数据分析部预测下月流失率将达 12%, 标记 320 名高价值玩家。LiveOps Agent 设计分级回流活动 (Level 0: $5 自动奖励; Level 2: $600 人工审批)。审批后 WinbackCampaignExecutor 自动发放奖励和推送, 召回率写入 CEO Memory。

### 1.4 核心价值

| 价值维度 | 量化指标 |
|----------|----------|
| 决策效率 | 从"人工 3 天" → "AI 3 小时" 完成跨部门决策链 |
| 人力成本 | 14 个 AI Agent 替代约 8-12 个初级岗位 |
| 数据闭环 | 100% 决策有数据支撑, 100% 执行有结果回测 |
| 经验沉淀 | 每次决策的成功/失败自动写入组织记忆, 复用率 ≥ 60% |
| 响应速度 | 异常检测到响应从"次日" → "分钟级" |

### 2.1 CEO 战略中心

| 维度 | 内容 |
|------|------|
| **Agent 名称** | CEO Agent |
| **职责** | 全局战略决策、跨部门资源调度、重大事项审批、每日例会主持 |
| **输入数据** | 各部门 KPI 汇总、GrowthLoop cycle 结果、待审批决策队列、组织健康度 |
| **输出结果** | 战略决策指令、预算分配方案、Go/No-Go 判定、每日 AI 简报 |
| **使用工具** | DecisionEngine (决策引擎)、ApprovalGate (分级审批)、CEO Memory (执行记忆) |
| **与其他 Agent 关系** | 向所有部门下发指令; 接收所有部门的结果回流; 与 AI 记忆中心双向同步 |
| **决策分级** | Level 0: 自动执行 (<$50) → Level 1: 模拟执行 ($50-$500) → Level 2: 人工审批 (≥$500) |

## 三、工作台设计

- **驾驶舱风格**: 一屏掌控全局, 关键指标前置

## 四、Agent 系统设计

### 4.1 Agent 生命周期

```
    ┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
    │ Created │────→│ Idle    │────→│ Running │────→│ Waiting │
    └─────────┘     └────┬────┘     └────┬────┘     └────┬────┘
                         ↑               │               │
                         │               ↓               ↓
                         │          ┌─────────┐     ┌─────────┐
                         └──────────│ Error   │     │ Approval│
                                    └────┬────┘     └────┬────┘
                                         │               │
                                         ↓               ↓
                                    ┌─────────┐     ┌─────────┐
                                    │ Retried │     │ Done    │
                                    └─────────┘     └─────────┘
```

**状态定义**:

| 状态 | 描述 | 触发条件 |
|------|------|----------|
| Created | Agent 刚注册, 未启动 | AgentRegistry.register() |
| Idle | 空闲, 等待任务 | 无任务或任务完成 |
| Running | 正在执行任务 | 接收到任务/事件 |
| Waiting | 等待审批 | 触发 ApprovalGate |
| Error | 执行出错 | 异常捕获 |
| Retried | 重试中 | Error 后自动重试 (最多 3 次) |
| Done | 任务完成 | 成功执行 |

### 4.2 Agent 通信方式

**三层通信架构**:

| 层级 | 机制 | 场景 | 延迟 |
|------|------|------|------|
| L1 事件广播 | MessageBus BROADCAST | 一对多通知 (churn_alert, behavior_analyzed) | 毫秒级 |
| L2 直接调用 | API/函数调用 | 一对一请求-响应 (Product→Designer GDD 传递) | 同步 |
| L3 持久化队列 | JSONL + 轮询 | 异步解耦 (CEO Memory 回流) | 秒级 |

**消息格式** (MessageBus):

```python
@dataclass
class AgentMessage:
    message_id: str          # UUID
    message_type: MessageType  # BROADCAST | REQUEST | RESPONSE
    subject: str             # 事件主题 (liveops:churn_alert)
    body: dict               # 事件负载
    sender: AgentIdentity    # 发送者
    recipients: list[str]    # 接收者 (BROADCAST 时为空)
    timestamp: str           # ISO-8601 UTC
    priority: int            # 0=高 1=中 2=低
    correlation_id: str      # 请求-响应关联 ID
```

### 4.3 任务分配机制

**任务分配策略**:

```
任务来源
  ├── CEO 指令 (手动/定时) → 直达目标 Agent
  ├── 事件触发 (MessageBus) → 订阅该事件的 Agent 自动响应
  ├── 数据驱动 (阈值告警) → DataAnalyst 触发 → 联动相关 Agent
  └── 人工创建 (Dashboard) → 指定 Agent 或部门
```

**优先级矩阵**:

| 优先级 | 触发条件 | 响应时间 | 示例 |
|--------|----------|----------|------|
| P0 紧急 | critical 告警 | < 1 分钟 | 异常检测到收入暴跌 50% |
| P1 高 | CEO 指令 | < 5 分钟 | CEO 触发 GrowthLoop |
| P2 中 | 事件驱动 | < 30 分钟 | churn_alert → Growth 响应 |
| P3 低 | 定时任务 | 按计划 | 每日 BI 报表生成 |

### 4.4 Memory 机制

**四层记忆架构**:

| 层级 | 类型 | 存储 | 保留期 | 用途 |
|------|------|------|--------|------|
| L1 工作记忆 | 短期 | 内存 | Session | 当前任务上下文 |
| L2 执行记忆 | 中期 | JSONL | 30 天 | execution_memory.jsonl — 执行结果记录 |
| L3 经验学习 | 长期 | JSONL | 永久 | execution_experience.jsonl — 成功/失败经验 + reward |
| L4 知识图谱 | 永久 | Graph | 永久 | Memory Graph — cross-domain 关联知识 |

**Memory 写入流程**:

```
Agent 执行动作
  → 写入 L2 execution_memory (success, action_type, result)
  → 评估 reward (positive/negative/neutral)
  → 写入 L3 execution_experience (reward, lesson, context)
  → 定期反思 → 提取模式 → 写入 L4 知识图谱
```

**Memory 查询流程**:

```
Agent 接收任务
  → 查询 L4 知识图谱 (相关 domain 的历史经验)
  → 查询 L3 经验学习 (类似场景的 reward)
  → 查询 L2 执行记忆 (最近相关执行)
  → 组装上下文 → 决策
```

### 4.5 Decision 机制

**三级决策架构**:

```
Level 0: 自动决策 (Agent 自主)
  ├── 阈值触发: ROAS < 80% → 自动暂停 campaign
  ├── 规则触发: 素材疲劳 > 0.8 → 自动生成变体
  └── 预算 < $50 → 自动执行
      ↓ 执行结果写入 Memory

Level 1: 模拟决策 (Dry-run)
  ├── 预算 $50-$500 → 生成方案 → 模拟执行 → 人工确认
  ├── 跨部门影响 → 生成影响评估 → 人工确认
  └── 新策略首次执行 → 模拟 → 人工确认
      ↓ 人工确认后执行

Level 2: 人工决策 (CEO 审批)
  ├── 预算 ≥ $500 → 必须人工审批
  ├── 不可逆操作 (删除 campaign, 下架游戏) → 必须人工审批
  └── 战略级决策 (新游立项, 品类扩张) → 必须人工审批
      ↓ 审批通过后执行, 可回滚
```

**DecisionGate 工作流**:

```
触发条件 → 评估决策级别
  ├── Level 0 → 直接执行 → 写入 Memory
  ├── Level 1 → 生成 dry-run 方案 → 写入 approval_queue
  │              ↓ CEO 审批
  │              ├── approve → 执行 → 写入 Memory
  │              └── reject → 记录原因 → 写入 Memory (负面经验)
  └── Level 2 → 生成完整方案 → 写入 approval_queue
                 ↓ CEO 审批
                 ├── approve → 执行 → 写入 Memory
                 └── reject → 记录原因 → 写入 Memory (负面经验)
```

### 6.8 Workflow Engine (GrowthLoop)

**6 阶段闭环**:

```
Phase A: 评估 (Assess)
  → 拉取 Meta Ads 数据 → 计算 ROAS/CAC → 评估健康度
Phase B: 信号 (Signal)
  → 检测异常 (ROAS < 阈值, 素材疲劳) → 生成 Signal
Phase C: 决策 (Decide)
  → 信号 → DecisionEngine → 生成 Action (pause/budget/suppress)
Phase D: 审批 (Approve)
  → ApprovalGate 分级 → Level 0 自动 / Level 1 dry-run / Level 2 人工
Phase E: 执行 (Execute)
  → 执行 Action → 写入 execution_memory
Phase F: 回测 (Measure)
  → 72h 后回测效果 → 写入 execution_experience → 更新知识图谱
```

**调度器**: `growth_loop_scheduler.py`
- 7×24 无人值守
- 可配置间隔 (默认 6 小时)
- 文件锁并发保护
- 状态持久化 + 断点续传
